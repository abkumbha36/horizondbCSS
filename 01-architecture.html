Component 1: Architecture, Control Plane / Data Plane Overview

Duration: 60-75 minutes

Learning objectives

  • Describe HorizonDB's overall architecture and where it fits in the Azure Data platform.
  • Explain the difference between control plane and data plane responsibilities.
  • Trace the lifecycle of a cluster from provisioning request to serving traffic.
  • Identify which HorizonDB components live in the control plane versus the data plane.
  • Explain how control plane operations (create, scale, patch, failover) affect the data plane.

1.1 What is HorizonDB

HorizonDB is a managed, PostgreSQL-compatible database service. As with most managed data platforms, its architecture is split into two conceptual planes:

  • Control plane: responsible for the lifecycle and management of resources - creating, updating, scaling, patching, and deleting clusters, along with enforcing configuration, RBAC, and orchestration of maintenance operations.
  • Data plane: responsible for actually serving customer traffic - accepting connections, executing queries, storing and retrieving data, and replicating for high availability.

This separation lets the platform scale management operations independently from customer query traffic, and it isolates faults so that, ideally, a control plane issue does not always translate into a data plane outage, and vice versa.

1.2 Control plane responsibilities

  • Resource provisioning (create/delete cluster, create/delete server group)
  • Configuration management (server parameters, firewall rules, networking configuration)
  • Orchestrating scaling operations (compute tier changes, storage scaling)
  • Coordinating patching and version upgrades
  • Triggering and coordinating failover
  • Managing backup policy and orchestrating restore requests
  • Exposing management APIs (ARM/RP layer) used by portal, CLI, and automation
  • RBAC, resource locks, and tagging

1.3 Data plane responsibilities

  • Accepting client connections on the database endpoint
  • Authenticating and authorizing individual database sessions
  • Query parsing, planning, and execution
  • Transaction management and locking
  • Storage engine operations - reads, writes, WAL (write-ahead log)
  • Replication to standby/replica nodes
  • Local caching (buffer pool, query cache where applicable)

1.4 High-level lifecycle flow

Customer/Portal/CLI | v [Control Plane / RP layer] |-- validates request, RBAC, quota |-- persists desired state |-- orchestrates provisioning workflow v [Compute + Storage allocation] | v [Data Plane bootstrap: PostgreSQL engine starts, networking attached, HA topology configured] | v Cluster reaches "Ready" state | v Client connections now served by [Data Plane] while ongoing management (scale/patch/failover) continues to be driven by [Control Plane]

1.5 Why the distinction matters for support

  • A "cluster stuck in provisioning" or "scaling operation failed" symptom generally points to the control plane (RP/orchestration layer).
  • A "cannot connect," "query is slow," or "queries are failing" symptom generally points to the data plane (engine, storage, network path to the engine).
  • Some issues span both planes: for example, a failed failover may show as a control plane operation failure, followed by data plane connectivity errors.
  • Correctly identifying which plane is affected shortens time-to-diagnosis and directs the case to the right internal team.

1.6 Build and deployment context (preview of Component 6)

Build and deployment issues - covered in depth in the Troubleshooting component - typically originate in the control plane, since they involve provisioning workflows, orchestration steps, and resource allocation before the data plane ever becomes reachable. Recognizing this up front helps you triage "cluster never became ready" tickets correctly.
